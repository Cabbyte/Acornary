# Daily intake — workflow version 1

Acornary maintains household inventory facts. Use the user's current authorized household and operator. Rules and candidates are live server data; this Skill contains no household taxonomy.

1. Understand the whole purchase. Collect explicit physical counts, known product identity, common location/dates, and per-piece differences. Omit unknown content quantity, dates, opening state and measurement accuracy. Do not interpret an unknown lifecycle as ACTIVE or infer contents from package capacity. Physical counts must be known. At most 100 items per task; agree on separate task boundaries before splitting.
2. Call `get_intake_context` once for all names, known product IDs and location clues. Inspect full paths, confirmed rules and aliases, relevant template fields, dependency revisions and each search coverage marker. A truncated or nonzero-offset page cannot establish absence. Query additional relevant candidates only when necessary for a concrete decision.
3. Reuse an explicitly identified existing SKU without asking to bootstrap unrelated rules. Names alone do not prove identity. Confirmed aliases and barcode matches can identify a product only when supplied facts do not conflict. Ask about actual ambiguity, differences, quantities or authorization together, not one optional field at a time.
4. Prefer direct product placement where the current rule permits it. Expand only inside an authorized branch, depth and naming constraints. Explain the semantic fit in `classification_reason`; this is a reasoned judgment, not an assertion of certainty or a permission token. Location and per-piece weight do not identify SKU or category. Do not invent catch-all or synonymous categories.
5. If the branch lacks a rule, a known conflict exists, or the intended extension is outside it, use the catalog governance workflow to propose the specific change. Distinguish a rule saved for future work from approval only for this exact batch. Wait for the user's card action. No `confirmed=true`, source label, confidence score, selection, or suggestion grants permission. Do not obtain or submit UI challenges through model tools. After confirmation, re-read changed rules and reconsider the batch; never force stale versions.
6. Call `commit_intake` once with the entire task, current policy and relevant object revisions, one idempotency key, shared defaults and per-instance overrides. Use the seven existing templates: product, catalog, clothing and device for SKU; lifecycle, contents and container for physical items. Omitted instance fields inherit defaults; explicit null location means no location. Do not call separate category/SKU/item writes for an intake draft. Existing facts and authorized ordinary intake need no extra app confirmation.
7. On timeout, retain the exact input/key. Use `get_intake_receipt` by operation ID or the current operator's key; if no result exists, retry the exact request. Never invent a fresh key for an unknown outcome. On revision/policy conflict, inspect the identified object and reconsider before submitting a new task. A failure means the whole intake transaction rolled back, not partial success.
8. Briefly report the actual item count, product names, complete location paths and meaningful per-piece differences from the receipt. Offer full identifiers/history only when needed. Separate actual reused/new records and unresolved facts. Different purchases have distinct physical items even when they reuse one SKU.

Never restructure, rename, merge, move historical categories or correct old inventory as a side effect of daily intake. If a historical conflict matters, describe it and propose a separate governance action. Semantic stability across wording, conversations and members needs real-host acceptance; passing structural checks alone does not prove it.
