## 与历史方案的区别

旧方案是单一暖色工作台，新方案区分日常和管理任务。日常弱化树与表格，管理保留密度；旧商品组先行默认改为实物默认/商品视图可切换。需要留意获得独立入口；设置仍共享。旧审计所建议的通用撤销、全部客户端搜索/排序、未知时区回退、默认隐藏容器后仍报服务器总数不继承。

旧方案宣称tokens单源，但theme.tsx仍硬编码；本稿明确迁移路径。旧文档的ui=legacy回退已不对应当前main代码；Phase3须新建受控功能切换，不假定老开关可用。已有协议、审批、Item身份和原请求恢复不因UI换代取消。

## B00 配色方案确认（2026-11-06）

用户原文：“这样，先锁定这四种配色可以切换。下一轮是不是要设计更多的组件？”

确认保留四套可切换外观预设：苔绿与石板蓝、杏橙与靛蓝、莓紫与青灰、浅白底的陶土与蓝灰。依据本轮配色对照板，每套包含日常与管理两种表现，使用近白背景与白色内容面。

配色预设与日常/管理模式是独立维度；不是四种业务模式，也不改变权限、导航语义或任务状态。共享组件通过 Token 应用配色，不复制四份组件。正式默认配色尚未单独确认，当前预览先展示苔绿不构成默认选择的批准。

本次只确认四套方案及可切换要求。字体、字号、密度、尺寸及完整交互状态仍待组件样板审阅，不能将本次确认扩展成 B00 全批通过。现有 6007/Storybook 样板仍是 R1，四套预设的正式 Token 落地尚未执行。

下一轮先用按钮和输入框样板确认剩余视觉基础，再按 B01 审阅 Button、IconButton、Input、Textarea、FormField、Badge；基础批准前不装配业务页面。遵守用户先讨论 UI、暂停回归测试的要求。

## Component Library RC1 执行规则（2026-11-06）

用户明确要求一次交付 70 个组件设计候选及 5 个组合场景。此决定取代此前“每批全部批准后制作下一批”的顺序：按工程依赖整合三轮，过程中不等待视觉批准；最终逐项审阅，所有组件仍标记待审阅。完整业务页面在组件审阅之后。

四套配色是独立于模式的外观维度。预览默认 sage/daily，不代表正式产品默认值获得批准。统一系统无衬线、桌面正文 14 px、手机正文/输入 16 px、标题 22 px 等尺度作为 RC1 制作基线，允许用户审阅后整体调整。旧 legacy Token 不变。Hover/Active 从强调色在生成阶段混黑 12%/24%，不单独维护。

正式源码使用受控 props 和意图回调；隔离场景提供 fixture 和展示状态，本轮不重写或接通正式写入状态机。预览的“审批”“回执”“设备反馈”只呈现传入事实，不能冒充服务端或设备证据。

本轮仅允许前端 TypeScript、Token/导入边界、预览和 Storybook 构建，以及代表性浏览器检查。Vitest、回归 Playwright、Docker CI、性能基准、真实 MCP/设备验收继续暂停；不推送、不部署。原 B00 工作已在本地提交 806dfff 保存，正式 Web/plugin 入口维持原实现。
