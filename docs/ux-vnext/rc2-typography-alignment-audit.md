# RC2 排版与对齐审阅

2026-11-06 · `codex/frontend-vnext` · 审阅代码：`a853848`。

**结论：保留当前配色、字体方向与信息结构，优先统一控件尺寸、主要事实的对齐基准和展开内容的位置。** 当前问题主要来自共享组件在组合后的规则冲突。继续逐页增加偏移量，会让桌面、窄容器及不同状态越来越难保持一致。

## 问题与建议

以下 P2 表示应优先统一的视觉问题，P3 表示后续整理项；不是本轮发现了生产阻断问题。

### A01 · P2 · 同一表单混用 36、44、46px 控件

**已确认。** 1440px 表单内，物品名称输入框高 36px，数量、单位及日期控件高 44px，位置 Combobox 内部控件 44px，加外框后约 46px。独立 DateInput 同样出现输入框 36px、日历与清除按钮 44px。搜索栏也有 36px 输入/文字按钮与 44px 图标按钮并排。

原因：`theme/vnext.css:71` 的匿名容器查询会匹配最近的窄字段容器，而不只是窄屏应用。`patterns/fields.css:10` 定义的 `domain-field` 在桌面双列表单内也只有 544px，因而触发触控尺寸。`controls.css:445` 的 Combobox 外层边框又叠加在内层最小高度之外。

**建议：** 将整体控件密度与字段内部重排分开。由明确的应用/面板密度作用域统一决定 36px 桌面或至少 44px 触控尺寸；字段宽度只决定一列、两列与换行。组合控件由最外框统一承担高度和边框，内部控件填充。图标的可见尺寸、可见外框与点击区域分别定义，保持触控目标且不挤占邻居或遮挡焦点环。

证据：[桌面表单](evidence/alignment-review/form-1440.png)。涉及 Input、IconButton、Combobox、DateInput、QuantityInput、SearchBar、LocationPicker 等共享组合。

### A02 · P2 · 同行事实对齐了容器顶部，没有对齐主要值

**已确认。** 桌面列表中，名称和可点击位置占 36px 行框并居中；数量占 21px 文字行框，直接贴顶。日期则在值上方先显示类型，所以数量实际对齐的是日期类型，日期值落在下一行。位置未知时又变成普通文字，和有链接的位置不在同一文字基准。

来源：`patterns/lists.css:222`、`patterns/facts.css`、`item-row.tsx`、`location-path.tsx`、`date-fact-value.tsx`。

**建议：** 列表采用统一的主要事实行。名称、位置、数量、日期值共享基准；规格、日期类型、来源等进入各自的次级行。日期类型仍必须可见，不删去或统称“过期”。已知、未知、估计、可点击与纯文本采用相同的视觉行框。主名称继续保持日常 16px/600、管理 14px/600，不通过放大所有文字解决层级。

证据：[桌面列表](evidence/alignment-review/search-1440.png)。窄屏数量/日期并列区域也应沿用相同规则。

### A03 · P2 · 展开详情会移动原来正在阅读的事实

**已确认两处。**

1. 搜索列表打开“依据与来源”后，日期值从 y=293.34 移到 y=332.59，下移约 **39.25px**。`facts.css:352` 的事实行使用 `align-items:center`，展开的详情与主要值仍是同一行的子元素。
2. 管理表格展开首行后，行高由 84.5 增至 172.5px。名称仍在 y=306.09，复选框由 y=325.84 移到 369.84，位置由 y=325.34 移到 369.34，均下移 **44px**。详情放在首个内容单元格内，其余单元格按整行高度居中。

**建议：** 摘要事实保留固定锚点，补充信息从摘要下方展开。日期详情独立占下一行；管理表格将详情放到独立的跨列区域，并保留正确表格语义、关联与焦点行为。不能仅对某个状态增加负 margin，也不应固定行高裁掉内容。ItemIdentity 的编号展开使用相近结构，应一并检查。

证据：[日期展开](evidence/alignment-review/date-expanded-1440.png)、[表格展开](evidence/alignment-review/table-expanded-1440.png)。来源：`date-fact-value.tsx:99`、`components/ui/data-table.tsx:377`、`patterns/facts.css:30`。

### A04 · P2 · 可排序表头与内容左边缘相差 16px

**已确认。** 管理表格“物品”表头文字从 x=337 开始，对应名称从 x=321 开始。普通位置列没有这层额外缩进。

原因：`components/ui/data-table.tsx:268` 把带横向 padding 的 Button 放入已有 padding 的表头；`controls.css:6` 再增加 16px。

**建议：** 单元格负责统一内容内边距，排序触发器不再额外移动文字。排序图标在标题后排列；触发范围可以覆盖表头空间。数字列、选择列、动作列分别采用一致的对齐规则，不将整张表简单居中。

### A05 · P2 · 列表每行独立计算列宽，混合动作时可能错列

**源码风险，未逐种动作组合复现。** `patterns/lists.css:289` 每个 ItemRow 各自计算网格，末列为 `auto`，前面的列按剩余空间分配。不同长度的按钮、有无更多动作、有无选择入口，会改变各行的位置、数量和日期起点。当前组合里的主要动作相同，不能用它证明混合行也对齐。

**建议：** 同一列表共享列宽定义，并保留一致的选择/动作槽位。可使用列表级网格、subgrid 或显式列模板；具体实现后再确认。长标题自然换行，缺失事实保留明确状态，不能以固定整行高度或省略关键值换取整齐。

### A06 · P2 · 工具栏对齐了组件外盒，内部实际控件错位

**已确认。** 搜索区域的筛选块包含范围说明，导致筛选按钮与搜索输入不在同一控件行。桌面 Shell 左侧家庭选择包含标签，右侧配色按钮却与整个字段顶部对齐，视觉上贴着标签而非选择框。

来源：`review/compositions/compositions.css` 的 `review-search-tools`、`patterns/navigation.css:182`。

**建议：** 顶栏明确分成“上下文/标签行”和“控件行”。搜索、筛选、扫码在同一实际操作行；范围说明放统一辅助行或紧凑状态区域。Shell 的配色动作与家庭选择的控件行对齐。手机继续按语义顺序重排，不强行把所有入口塞成一行。

### A07 · P3 · 提示按钮和默认段落边距破坏间距节奏

**源码风险。** `controls.css:162` 的标签帮助按钮高 44px、上下各负 margin 8px，净占位仍约 28px；普通标签在桌面只有约 21px，在手机约 24px。混排有/无帮助入口时，输入框起点可能差 7/4px。`OperationReceipt`、受限 `PendingOperationBanner` 和部分 `NoteEditor` 分支保留普通 `<p>` 默认 margin，又叠加容器 gap；状态改变时可能突然多出空白。

**建议：** 单行标签采用一致的行框，帮助入口扩大点击区域而不改变文字排版高度；多行标签正常增长。布局中的状态/说明段落显式归零外边距，由容器管理间距。长篇笔记采用独立 prose 段落规则，不能全局删掉阅读内容的段落间隔。错误直接出现并自然增加高度，不为空的错误状态预留一整行。

建议间距角色继续使用现有尺度：字段内部 8px，同组字段 16px，组间 24px，主要区域 32px。不是要求把所有间隔统一成一个数。

### A08 · P3 · 手机数量依据字段出现第三种无意义宽度

**已确认。** 窄屏数量与单位占两列，下一行的“数量依据”虽然跨两列，却受 `fields.css:277` 的 `max-width:16rem` 限制。390px 时它宽 256px，而整组宽 358px；320px 时整组宽 288px，仍是 256px。形成不对应任何相邻边缘的右侧空白。

**建议：** 数量与单位保留相邻关系；依据另起一行时占满该组宽度。日期、位置、普通选择器的左右边界遵循同一表单网格，只有内容本身确实短且语义明确的控件使用紧凑宽度。

证据：[320px 表单](evidence/alignment-review/form-320.png)。该页面实测 `scrollWidth=320`，没有横向溢出；这不代表全部组件和大字体场景已通过。

## 建议统一的排版规则

1. **保留字号体系，固定用途。** 页面标题 22/600、分组标题 16/600、桌面正文/控件 14、手机正文/输入 16、辅助信息 13；正文行高 1.5，标题 1.3。不新增一批接近但不同的字号。日常物品名 16/600、管理物品名 14/600。
2. **区分文字基准与点击区域。** 主要事实按文字行框对齐；输入框按外框对齐；图标在所属控件中居中。点击目标不能靠改变旁边文字位置来满足。
3. **同级共享网格。** 页面标题、工具栏和主体沿同一内容边线；同一列表共享列；同一表单行共享标签/控件规则。保留桌面两列、手机单列及现有留白方向。
4. **展开只增加补充区域。** 摘要值、选择入口、行操作保持锚点；来源、完整 ID、版本、历史和帮助继续可达。
5. **间距由一个层级负责。** 容器 gap 与子元素 margin 不重复计算；正文段落与布局说明分别定义。减少偶然空白，保留真实分组。
6. **长内容自然生长。** 长名称、未知值、错误、日期类型和长位置路径不压小字体；允许换行，并检查同组基准与操作入口。当前长附件、历史前后值未发现足以要求重做结构的问题。

这些规则是本轮建议，尚未实施或冻结；不改变业务流程、事实类型与模式权限边界。

## 建议修正顺序及复审条件

| 顺序 | 修正范围 | 下轮人工复审应看到的结果（当前未通过） |
| --- | --- | --- |
| 1 | 密度作用域、控件外框、标签行 | 同一密度下的 Input/Select/Combobox/DateInput 外框同高；图标与文字位置稳定；触控目标及焦点不受损 |
| 2 | 事实主行、列表共享列、表格详情 | 主要值对齐；混合动作不使各行错列；展开日期、ID、表格详情不移动原摘要 |
| 3 | 搜索工具栏、Shell 顶栏、表单宽度 | 实际控件行对齐；窄屏按语义重排；无任意截短的字段宽度 |
| 4 | 段落与状态间距 | 帮助/错误/恢复/只读/长文本切换后节奏一致，没有额外默认 margin 或重叠 |
| 5 | 五个组合统一复审 | 桌面、窄 iframe、手机都能连续阅读；记录问题修复前后截图，仍由用户作视觉批准 |

## 静态扫描与限制

使用本地 Impeccable 检测器，仅扫描 `apps/web/src/ui` 与 `apps/web/review`：

```text
impeccable detect --json --scope layout apps/web/src/ui apps/web/review
impeccable detect --json --scope type apps/web/src/ui apps/web/review
```

两条命令 exit code 均为 0。layout 没有规则命中；type 有 9 条 `design-system-font-size` advisory，来自 3 个文件。检测器未输出扫描总文件数，不能把命中文件数当作覆盖数量。

- 5 条来自旧 `apps/web/src/ui/layout.css`：本轮不修改旧 UI。
- 4 条来自审阅外框 `library.css`、`review.css` 的 18/20/22px：工具对照旧 `DESIGN.md` 字号表，22px 本身符合当前候选。它们不能直接认定为产品组件缺陷；审阅外框可在后续按统一文字角色核对。
- 静态零命中不代表视觉正确。以上浏览器实测的尺寸混用、日期和表格展开漂移均不由该规则扫描识别。
