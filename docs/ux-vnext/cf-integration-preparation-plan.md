# CF 集成准备与 Phase 2 收尾执行方案

日期：2026-11-11（Asia/Shanghai）。状态：用户已批准执行；已建立 CF 集成分支并本地合并，实施结果见 phase2-cf-report.md。未推送、未部署。本文调整前端项目的集成目标，不新增独立项目阶段。

## 1. 目标与阶段边界

新前端以 Cloudflare 分支为开发和未来发布主线，后续只向 CF 环境发布。当前非 CF 的正式前端、后端、数据库和域名路由继续保留。Android 共用业务协议和客户端逻辑，先保留正式/CF 双安装包，后续再实现同一 App 的受控环境切换。

本轮归属 **Phase 2 收尾：CF 开发基线、正式候选应用层、功能对等映射和双后端兼容准备**。本轮不连接真实库存执行、不部署 CF、不替换任何线上入口。Phase 2 验收后，Phase 3 才进行 CF 真实协议接线和分批发布。

用户现有约束持续有效：回归测试暂停；不得通过推送触发 CI 绕过暂停；不部署、不改正式数据，不改领域模型，不丢弃草稿、审批、revision 或幂等机制。RC6 组件和已批准流程保留；新增产品语义变更单独记录。组件工作台、页面审阅和修改意见入口持续保留。

阶段状态必须区分：代码候选完成 / 有限构建检查通过 / 回归通过 / 用户验收 / CF 已部署 / 正式迁移。暂停期间最多交付前两项，不能宣称 Phase 2 工程验收完成。

## 4. 兼容性目标与差异分类

目标是同一个受支持客户端在两种后端上具有一致业务语义，不要求域名、令牌、内部数据库或每次生成的 ID/时间戳字节相同。

维护两份互相关联的清单：

- 功能替换清单：旧入口、用户任务、新入口、真实查询/命令、权限、错误恢复、Web/MCP/Android 支持范围、验收证据。
- 接口兼容矩阵：非 CF 线上版本、CF 对应实现、共享 schema、响应/错误语义、正常/边界/失败序列、当前证据及未验证项。

每个差异归类为：既有功能退步 / 非 CF 与 main 版本差异 / CF 运行时差异 / 新前端尚未接线 / 已批准新能力 / 真正契约缺口。不得用新增能力掩盖旧功能遗漏，也不因新能力缺口否定全部既有能力的迁移。

兼容矩阵至少包含：

| 范围 | 必须对齐的行为 |
| --- | --- |
| 身份、家庭、权限 | 账号和家庭隔离、命令可用性、错误状态；会话不跨环境复用 |
| 查询 | 筛选、排序、分页边界、覆盖范围、总数语义、未知事实 |
| Item / SKU / GROUP | 身份与父子关系、属性模板/版本、共有资料与单件覆盖 |
| 数量与日期 | decimal string、精度/单位、未知与零、日期类型/来源/时区 |
| 写入 | 审批、revision、原子批量、危险操作、实际影响对象 |
| 恢复 | 同键重放、异参数冲突、丢回执、原请求查询、失效审批 |
| 历史与附件 | 事件归属/顺序、笔记范围、私有访问、上传完成及删除语义 |
| Android v1 | config、PKCE、snapshot/detail/history、命令、operation lookup、刷新与撤销 |
| MCP | 公开工具、schema、OAuth、UI resource、宿主特有限制 |

54 个公共操作检查不能替代 HTTP、Android、附件或 OAuth 全部接口检查。对齐目标首先是已部署非 CF 的受支持能力集合；main 中比线上新的变化另列。未来新增后端能力若不同时提供给旧端，就必须标记为版本能力差异，不能再声称两端完全相同。

本轮可以编写兼容用例、夹具和比较规则，但不运行暂停中的差分/回归。后续差分必须在两个隔离测试实例上使用同一组已知种子和操作序列，禁止把正式库存当测试靶。

## 5. 正式候选应用层收尾

复用已经存在的 `features/api`、`features/inventory`、`features/writes`、Session/Connection 和共享契约，优先抽取纯逻辑，不重新发明业务状态机。不将 review Journey、本地世界执行器或测试幂等逻辑直接用于生产。

建议职责：

| 层 | 交付内容 |
| --- | --- |
| 应用 Shell / 路由 | 双模式、页面注册、返回上下文、深链接与作用域入口 |
| 读取接口 | 规范化事实、真实分页/排序/筛选、缓存覆盖和失效边界 |
| 操作会话 | 目标 UUID、原值、输入、期望版本、审批、原请求键/参数、状态和回执 |
| 平台接口 | 存储、Web/MCP 通信、扫码、打印、导航能力 |
| fixture 装配 | 唯一示例数据/执行注入点、故障场景、审阅工具 |

应用根持有任务，页面和表单只是受控视图。不得以页面卸载、模式切换、窗口旋转重建任务。提交前可靠保存原请求；持久化失败不发送；未知结果只恢复原请求；冲突保留输入并重新核对；账号/家庭变化隔离旧响应。

Scope 包含环境、账号、家庭；任务还绑定客户端/数据集及会话代次。Web 本轮只面向 CF 的正式接线目标，不增加面向普通用户的双后端开关。隔离试用和真实 CF 入口通过明确装配边界区分，不以生产可随意开启的 mock 开关区分。

Trial RC1 的 localStorage 日志 + IndexedDB 镜像是试用选择，不能不经审查替代正式 Web/MCP 的持久化与宿主回读要求。本轮不读取、迁移或重写现有正式草稿。

现有 React 页面、70 组件、四配色、双模式保留。与生产适配无关的 UI 继续原样，发现真实契约影响重大产品行为时记录变更并再确认；普通布局修改通过原审阅入口处理。

## 6. CF 构建隔离与预览

本轮整合三个本地入口：6006 组件、6007 页面、6008 连续试用，仍仅注入隔离数据。生产候选构建不得含 fixture、意见服务、测试角色、模拟写入、测试扫码或打印适配器。

在 CF 资产构建链中准备新候选入口和明确选择机制；本轮保留旧 CF 入口默认绑定，不发布、不自动接业务。Web 与 MCP 的资源构建分别保持有效；不能把 Web 构建成功当作自包含 MCP UI 验收。

边界检查扩展到正式候选应用层，验证：

- 新 UI 无 Ant 组件导入；原入口保留 Ant 依赖至功能对等完成。
- 正式候选无 review/fixture 依赖；试用配置无业务代理和生产 Service Worker。
- CF 资源/域名/发布配置仅指向 CF；不引入非 CF 的服务器部署脚本。
- 契约和现有业务机制无为了 UI 而放宽的分支。

原意见记录按稳定组件/page ID、版本、配色、宽度和任务上下文继续关联。新工作树与旧工作树的意见去重按提交 ID，不重复归档为新意见。

## 7. Android 本轮范围与后续设计

本轮保留现有正式包与 `cfPreview` 两包。交付同 App 环境切换的接口、状态和迁移设计，不在本轮向已安装正式客户端发布开关。

后续建议内置两个固定服务配置，而非任意输入 URL：

- 服务 ID、展示名称、HTTPS origin、API resource、回调和端点约束。
- 独立令牌保管、缓存命名空间、草稿/未决请求、打印任务和后台同步作用域。
- 现有服务能力从真实配置/权限读取；不凭环境名称推断可执行命令。

当前 `SessionContext.scope` 只有账号/家庭，环境隔离依赖独立应用 ID；同 App 时需要改为环境 + 账号 + 家庭。相同 UUID 在两个数据库出现时仍是两个环境中的对象，不能据此合并缓存或任务。

切换规则冻结为：

| 状态 | 环境切换规则 |
| --- | --- |
| 普通浏览/已保存草稿 | 保存当前作用域，取消读取，切到另一环境独立登录/恢复 |
| 写入提交中 | 阻止切换，先确定原尝试状态 |
| 结果不确定 | 若已可靠持久化，可明确保留并离开；只在原环境恢复，不转发到另一后端 |
| 登录/令牌刷新中 | 取消或结束原流程；旧回调/旧响应不得进入新环境 |
| 打印发送中 | 先保留并核对原任务；切换不导致重打 |
| 后端不可达 | 显示当前环境状态，不自动故障转移到另一套库存 |

首次升级的旧缓存只可归到已知原正式环境；不能重新解释成 CF 缓存。旧未决请求保留原服务归属。登录会话不跨域迁移；两个 origin 的 App Links、OAuth client/resource、回调及签名指纹分别校验，保留严格 PKCE/state 检查。旧二维码域名在 CF 试用中不能被静默改写为可写目标；跨环境标签跳转只在明确的数据集映射与用户选择下开放。

## 9. 检查与阶段门槛

回归暂停期间允许：前端/CF TypeScript、`cf:contracts` 静态冻结契约比较、Token/边界/目录检查、独立 UI 构建、CF 资产构建和确认无远端副作用的 dry-run、必要 APK 编译（不安装）、集中人工预览检查。

暂停期间不运行：Vitest/Playwright 回归、workerd 业务测试、Docker/数据库差分、远端写入验收、性能基准、实机/真实 MCP 验证；不推送触发 CI、不部署。脚本先读取后执行，不能用名称为 build 的组合脚本间接运行暂停任务。

**本轮代码候选完成条件：**

1. CF 派生工作树承接全部前端成果，用户原工作树与线上应用未改。
2. 旧必需功能均有可追踪新入口/接口/差距；不能判定的条目明确未证实。
3. 正式候选应用层与试用执行器分开，根任务会话复用现有业务机制，页面不执行业务 I/O。
4. 本地三个审阅入口可用，原意见/批准记录保留。
5. Android 双后端方案覆盖存储、身份、回调和未决写入，而非仅 base URL。
6. 有限检查有实际结果；回归、真机、真实接线保持未通过；用户审阅后才能冻结候选。

**Phase 2 完成门槛：**用户明确恢复回归，完成所需组件/状态/路由/持久化/响应式/无障碍/性能与构建验证及用户验收。只要回归仍暂停，阶段维持“工程验收待完成”，不能进入真实业务集成或发布。

## 10. Phase 3 和后续概括

Phase 2 验收后按依赖推进：

1. **首个真实闭环**：在本地 workerd 或专用 CF 测试家庭内完成真实身份/家庭 → 搜索/单件档案 → 部分使用 → 余量/历史 → 丢回执恢复。非 CF 对照在隔离实例运行，绝不向线上库存发测试写入。
2. **扩展日常接线**：入库、移动、开封、日期、笔记、附件与留意；保留原子性、未知事实和现有审批。
3. **管理与其余入口**：目录、位置、属性、模板、策略、批量、历史/纠错、账号、打印、检查器和 MCP。只有实际对等验收的功能才能切换新入口；未通过的保留旧 CF 路径。
4. **双后端兼容证据**：相同客户端版本和操作序列在两套隔离后端运行；核对终态、事件、revision、错误码和回执重放。认证配置差异显式参数化，不掩盖业务差异。
5. **Android**：先完成现有双包对照/实机验收，再实施同 App 的环境选择、旧本地数据迁移及旧响应隔离；不自动更新正式设备。摄像头、App Links、后台同步、AOD、蓝牙/打印分别记录实机结果。
6. **CF 限定发布**：按现有 release manifest、干净提交、同提交 CI 和 CF 专用发布流程部署。UI 改动仍会进入 Worker/资产整体发布，核对完整发布物，不把它当作“只传几个静态文件”。保留旧 CF UI 与可回退版本；不得删除已有 DO 类/绑定或跨未验证数据迁移回退。
7. **连续试用和正式切换准备**：保留原非 CF 服务，观测 CF；正式迁移前暂停旧端写入，取得新一致快照，验证 ID/版本/历史/回执/附件，准备账号/域名/二维码/安卓兼容。测试写入不回灌，最终迁移不复用有试用写入的旧副本。
8. **最终切换/回滚**：在明确的发布授权下实施。CF 开放正式写入前可以回退入口；开放写入后不能只改回旧地址，须先解决增量数据、回执和重新认证问题。最终是否保留原域名指向新后端，作为发布方案中的明确决策。

整个期间非 CF 继续作为正式事实来源，CF 为隔离验证环境。最终切换后才变更事实来源。Web 新前端只在 CF 发布，并不要求同时为非 CF 发布新 UI；两后端的共同 API 能力维持同一业务契约。
